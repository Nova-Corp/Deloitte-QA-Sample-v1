What is the difference between Struct and Class in Swift? Fundamental

+

This is one of the most frequently asked Swift questions. The core distinction is value type vs reference type.

FeatureStruct (Value Type)Class (Reference Type)
MemoryStack (usually)Heap
Copy behaviorDeep copy on assignmentShared reference
Inheritance❌ Not supported✅ Supported
Deinitializer❌ No deinit✅ Has deinit
MutabilityRequires mutating keywordMutable by default
Identity check❌ No ===✅ === operator
Thread safety✅ Inherently thread-safe⚠️ Requires synchronization
ARC❌ Not reference counted✅ Reference counted
Swift 
// VALUE TYPE — each variable holds its own copy
struct Point {
    var x: Double
    var y: Double
}

var a = Point(x: 1, y: 2)
var b = a        // b is a COPY of a
b.x = 10
print(a.x)       // 1 — 'a' is unchanged ✅

// REFERENCE TYPE — variables share the same instance
class Circle {
    var radius: Double
    init(radius: Double) { self.radius = radius }
    deinit { print("Circle deallocated") }
}

let c1 = Circle(radius: 5)
let c2 = c1      // c2 points to the SAME object
c2.radius = 99
print(c1.radius)  // 99 — c1 is also changed ⚠️
print(c1 === c2)  // true — same identity
💡
Interview Tip

Apple recommends using structs by default. Use classes only when you need inheritance, reference semantics, or Objective-C interoperability. Mention Copy-on-Write (COW) optimization for Swift collections (Array, Dictionary, Set) — they're structs but copy only when mutated.

Explain Swift Concurrency in depth (async/await, actors, structured concurrency) Advanced

+

Swift Concurrency (introduced in Swift 5.5) provides a modern, safe, and structured way to write concurrent code, replacing completion handler patterns.

Core Components

  • async/await — Write asynchronous code that reads like synchronous code
  • Structured Concurrency — Tasks are organized in a parent-child hierarchy via async let and TaskGroup
  • Actors — Reference types that protect mutable state from data races
  • @Sendable — Marks closures and types safe to pass across concurrency boundaries
  • @MainActor — Ensures code runs on the main thread (UI updates)
Swift 
// 1️⃣ async/await — Clean asynchronous code
func fetchUser(id: Int) async throws -> User {
    let url = URL(string: "https://api.example.com/users/\(id)")!
    let (data, _) = try await URLSession.shared.data(from: url)
    return try JSONDecoder().decode(User.self, from: data)
}

// 2️⃣ Structured concurrency with async let
func loadDashboard() async throws -> Dashboard {
    async let profile = fetchUser(id: 1)          // Runs concurrently
    async let posts = fetchPosts(userId: 1)       // Runs concurrently
    async let notifications = fetchNotifications() // Runs concurrently
    
    return try await Dashboard(
        profile: profile,
        posts: posts,
        notifications: notifications
    )
}

// 3️⃣ TaskGroup for dynamic concurrency
func fetchAllUsers(ids: [Int]) async throws -> [User] {
    try await withThrowingTaskGroup(of: User.self) { group in
        for id in ids {
            group.addTask { try await fetchUser(id: id) }
        }
        var users: [User] = []
        for try await user in group {
            users.append(user)
        }
        return users
    }
}

// 4️⃣ Actor — Thread-safe state management
actor BankAccount {
    private var balance: Double = 0
    
    func deposit(_ amount: Double) {
        balance += amount  // No race condition — actor-isolated
    }
    
    func getBalance() -> Double { balance }
}

// 5️⃣ @MainActor — UI updates
@MainActor
class ViewModel: ObservableObject {
    @Published var users: [User] = []
    
    func refresh() async {
        let fetched = try? await fetchAllUsers(ids: [1, 2, 3])
        users = fetched ?? []  // Safe — guaranteed on main thread
    }
}
💡
Interview Tip

Emphasize that Swift concurrency provides compile-time safety against data races (unlike GCD). Mention Task cancellation propagation and how Task.checkCancellation() enables cooperative cancellation.

How do you handle large images efficiently in iOS? Important

+

Loading large images directly into memory can cause memory spikes and OOM crashes. Here's the professional approach:

Key Strategies

  • Downsampling — Resize at decode time using ImageIO framework, never decode the full-resolution image
  • Lazy Loading — Load images on-demand as cells appear (UICollectionView prefetching)
  • Caching — Multi-layer cache: NSCache (memory) + disk cache (e.g., Kingfisher, SDWebImage)
  • Thumbnail API — Use prepareThumbnail(of:) (iOS 15+) or UIImage.preparingThumbnail
  • Progressive Loading — Show low-res placeholder → load full image asynchronously
Swift — Downsampling with ImageIO 
import ImageIO

func downsample(imageAt url: URL, to pointSize: CGSize, scale: CGFloat) -> UIImage? {
    let maxDimensionInPixels = max(pointSize.width, pointSize.height) * scale
    
    let options: [CFString: Any] = [
        kCGImageSourceCreateThumbnailFromImageAlways: true,
        kCGImageSourceShouldCacheImmediately: true,        // Decode immediately
        kCGImageSourceCreateThumbnailWithTransform: true,
        kCGImageSourceThumbnailMaxPixelSize: maxDimensionInPixels
    ]
    
    guard let imageSource = CGImageSourceCreateWithURL(url as CFURL, nil),
          let downsampledImage = CGImageSourceCreateThumbnailAtIndex(imageSource, 0, options as CFDictionary)
    else { return nil }
    
    return UIImage(cgImage: downsampledImage)
}

// Usage: A 12MP photo (4032×3024) loads only the pixels needed
let thumbnail = downsample(imageAt: photoURL, to: CGSize(width: 200, height: 200), scale: UIScreen.main.scale)
⚠️
Common Mistake

Never use UIImage(named:) for user-generated content — it caches images in memory permanently. Use UIImage(contentsOfFile:) instead, which doesn't auto-cache.

What is the Singleton pattern? How do you implement it in Swift? Fundamental

+

A Singleton ensures only one instance of a class exists throughout the app's lifecycle. Swift makes this trivially safe with static let.

Swift 
final class NetworkManager {
    static let shared = NetworkManager()   // Thread-safe, lazy init
    
    private init() { }  // Prevent external instantiation
    
    private let session = URLSession(configuration: .default)
    
    func fetch(from url: URL) async throws -> Data {
        let (data, _) = try await session.data(from: url)
        return data
    }
}

// Usage
let data = try await NetworkManager.shared.fetch(from: someURL)

When to Use (and Avoid)

  • ✅ Good: Logging, Analytics, Network layer, Database manager
  • ❌ Bad: When you need testability (hard to mock) — prefer Dependency Injection with a protocol
💡
Interview Tip

Mention that static let in Swift is thread-safe by default (dispatch_once under the hood). Discuss the tradeoff: Singletons make unit testing harder — suggest the "Singleton + Protocol" pattern where you inject the singleton via a protocol for testability.

01

Flutter Full Basics: Architecture, The Three Trees, BuildContext, and Keys Fundamental

+

Interviewers ask this to test if you truly understand Flutter's internals rather than just assembling widgets.

1. Architectural Layers

  • Framework (Dart): Everything you touch daily — Material/Cupertino widgets, rendering, animation, gestures, and foundation services.
  • Engine (C/C++): The muscle — handles Skia / Impeller graphic rendering (Vulkan on Android, Metal on iOS), Dart runtime/GC, text layout (HarfBuzz), and platform channel message dispatching.
  • Embedder (Platform-Specific): Coordinates with the underlying OS (surface creation, thread coordination, native event loop, plugins). Written in Java/Kotlin (Android), Objective-C/Swift (iOS), and C++ (Desktop).

2. The Three Trees of Flutter

TreeNatureResponsibilityLifecycle
Widget TreeImmutable, lightweight blueprintsDeclares UI configuration (how UI should look)Recreated frequently on every build
Element TreeMutable, structural spineManages lifecycle, holds state, acts as the bridge between Widget and RenderObjectPersists across builds; reconciled via keys and runtime types
RenderObject TreeMutable, heavy layout/paint objectsComputes constraints, sizing, layout, hit-testing, and drawing pixels on canvasOnly instantiated or updated when geometric/visual properties change

3. What is BuildContext Really?

BuildContext is literally the Element corresponding to the widget in the Element tree. It gives the widget its relative position in the hierarchy, allowing methods like Theme.of(context) or MediaQuery.of(context) to climb up ancestors to find inherited data.

4. Hot Reload vs Hot Restart

  • Hot Reload: Injects updated Dart source code directly into the running Dart VM. Keeps app state intact; does not re-execute initState() or static initializers.
  • Hot Restart: Re-compiles application code, clears the entire Dart VM memory/state, and re-executes from main() and fresh initState().

5. Flutter Keys — When and Why?

Keys preserve state when widgets move positions or when items are reordered, inserted, or removed from collections.

  • ValueKey('user_123') — Compares by equality of a primitive or string (ideal for list item IDs).
  • ObjectKey(userModel) — Compares by object reference/identity.
  • UniqueKey() — Generates a unique identity every build (forces complete recreation).
  • PageStorageKey('feed_scroll') — Preserves scroll offset across tab switches.
  • GlobalKey<FormState>() — Universally unique across the entire app; allows accessing state or RenderBox across separate subtrees (use sparingly due to performance overhead).
💡
Interview Tip

Explain that when setState() is called, Flutter does NOT redraw the entire screen. It marks the Element as dirty, walks down the tree, compares the new Widget's runtimeType and key with the existing Element. If identical, it only updates the existing Element and RenderObject, making Flutter's reconciliation algorithm O(N).

Explain the Flutter Widget Lifecycle and App Lifecycle Important

+

StatefulWidget Lifecycle

  1. createState() — Framework calls this to create the State object
  2. initState() — Called once when State is inserted into the tree (initialize controllers, subscriptions)
  3. didChangeDependencies() — Called when inherited widgets change (e.g., Theme, MediaQuery)
  4. build() — Called every time the widget needs to render (must be pure, no side effects)
  5. didUpdateWidget() — Parent rebuilds with new widget config (compare old vs new)
  6. setState() — Triggers a rebuild by marking the state as dirty
  7. deactivate() — State is removed from the tree (may be reinserted)
  8. dispose() — Called once; permanent removal. Clean up controllers, streams, subscriptions

App Lifecycle (AppLifecycleState)

Dart 
class MyApp extends StatefulWidget {
  @override
  State<MyApp> createState() => _MyAppState();
}

class _MyAppState extends State<MyApp> with WidgetsBindingObserver {
  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addObserver(this);  // Register observer
  }

  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    switch (state) {
      case AppLifecycleState.resumed:   // App is visible and responding
        print('App resumed — refresh data');
        break;
      case AppLifecycleState.inactive:  // App is inactive (phone call overlay)
        print('App inactive — pause animations');
        break;
      case AppLifecycleState.paused:    // App is in background
        print('App paused — save state');
        break;
      case AppLifecycleState.detached:  // App is about to be terminated
        print('App detached — final cleanup');
        break;
      case AppLifecycleState.hidden:    // App hidden (iOS multitasking)
        print('App hidden');
        break;
    }
  }

  @override
  void dispose() {
    WidgetsBinding.instance.removeObserver(this); // Always remove!
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => MaterialApp(home: HomeScreen());
}

Dart is single-threaded. How can Flutter make API calls and show animations simultaneously? Advanced

+

This is a top interview question. The answer lies in Dart's Event Loop and non-blocking I/O.

How It Works

  • Dart runs on a single thread with an Event Loop that processes events from two queues:
    • Microtask Queue — High priority (Future.microtask, scheduleMicrotask)
    • Event Queue — Regular events (I/O, timers, UI gestures, Future callbacks)
  • async/await does NOT block the thread — it registers a callback and yields control back to the Event Loop
  • The network I/O happens at the OS level (outside Dart) — Dart's event loop is free to render frames at 60fps
Dart — Event Loop in Action 
// This does NOT block the UI thread!
Future<void> fetchData() async {
  // 1. HTTP request is delegated to the OS
  // 2. Dart's event loop is FREE to process UI events
  // 3. When response arrives, callback is added to event queue
  final response = await http.get(Uri.parse('https://api.example.com/data'));
  
  // This runs only AFTER the response arrives
  setState(() {
    data = jsonDecode(response.body);
    isLoading = false;
  });
}

// For CPU-INTENSIVE work, use Isolates (true parallelism)
Future<List<int>> heavyComputation(List<int> data) async {
  // Runs on a SEPARATE thread — won't block UI
  return await Isolate.run(() {
    // Complex sorting, parsing, image processing...
    return data.where((n) => isPrime(n)).toList();
  });
}

// Or use compute() for simpler cases
final result = await compute(parseJson, jsonString);
💡
Interview Tip

Key distinction: async/await handles I/O-bound work (network, file system) — no extra thread needed. Isolates handle CPU-bound work (JSON parsing of large payloads, image processing) — these are true OS threads with their own memory. Mention that Isolate.run() (Dart 2.19+) is the modern API replacing compute().

04

If an API takes 30 seconds to respond, how does the progress indicator continue running without freezing the UI? Advanced

+

This question tests your deep understanding of I/O versus CPU bounds, the Vsync render pipeline, and Dart's Event Loop.

The Core Mechanics

  1. Asynchronous Non-Blocking Socket I/O: When you call await http.get(...) or await dio.get(...), Dart's HttpClient hands the socket request down to the underlying C++ Engine, which registers an asynchronous socket event with the OS kernel (via epoll on Linux/Android or kqueue on iOS/macOS). Dart does not spin or poll; the main thread immediately returns control back to the Event Loop.
  2. The Vsync 60fps/120fps Engine Pulse: The display hardware fires a Vsync pulse every 16.6ms (at 60Hz) or 8.3ms (at 120Hz). Flutter's SchedulerBinding listens to these pulses and schedules a frame.
  3. Animation Ticker Execution: A CircularProgressIndicator operates on an AnimationController driven by a Ticker. On every single Vsync pulse, the Ticker fires, updates the rotation angle, marks the render object dirty via markNeedsPaint(), and draws the next frame on the canvas.
  4. Event Queue Separation: During the entire 30 seconds, the event loop remains completely empty and free between Vsync ticks. When the API response finally arrives at second 30, the OS signals the engine, which queues a single I/O completion callback into the Event Queue. Dart then resumes your async function after the current frame finishes.

I/O-Bound (Network/File)Waiting 30 seconds on REST API✅ Zero jank / 60fps animations (Thread is idle)Standard async / await
CPU-Bound (Computation)Parsing a 50MB JSON string or AES encrypting a large file❌ UI Freezes / Drops frames (Event loop is blocked)Offload to Isolate via Isolate.run()
Dart — Non-blocking vs Blocking 
// ✅ WON'T FREEZE: 30-second network call allows 60fps animations
Future<void> fetchSlowApi() async {
  setState(() => _isLoading = true); // Spinner starts animating via Ticker
  
  // OS handles network wait asynchronously; Dart event loop is 100% free!
  final response = await dio.get('https://api.example.com/slow-30s-data');
  
  // ⚠️ WILL FREEZE if 50MB payload is parsed synchronously on main thread:
  // final data = jsonDecode(response.data); // FREEZES UI FOR 800ms!

  // ✅ CORRECT FIX for heavy computation:
  final data = await Isolate.run(() => jsonDecode(response.data));

  setState(() {
    _data = data;
    _isLoading = false;
  });
}
💡
Interview Tip

Clearly state: "Network latency is waiting time, not computing time." The UI freezes only when Dart's CPU instructions occupy the thread for more than 16ms (e.g. large JSON parsing, image filtering, heavy crypto), which is why CPU-heavy work requires Isolates.

05

Have you worked with threads in your project? How do you handle background processing in Flutter? Advanced

+

Dart handles threading differently from Java/C++. In Dart, threads are encapsulated inside Isolates.

Key Concepts of Dart Isolates

  • No Shared Memory: Isolates do not share heap memory. There are no race conditions, synchronized blocks, or mutex deadlocks.
  • Message-Passing Communication: Isolates communicate exclusively by passing serialized messages through SendPort and ReceivePort.
  • Dedicated Event Loop: Every isolate has its own independent memory space and event loop.

When to Use Isolates

  • Parsing massive JSON payloads (>1MB)
  • Cryptographic encryption, decryption, and hashing (AES, RSA, SHA-256)
  • Image manipulation, resizing, and PDF generation
  • Local database migrations or complex filtering of tens of thousands of records
Dart — Isolate.run vs Two-Way Port Worker 
// 1️⃣ ONE-SHOT WORK: Modern Isolate.run (Dart 2.19+)
Future<List<User>> parseLargeUsersJson(String rawJson) async {
  // Spawns isolate, executes closure, returns result, shuts down isolate
  return await Isolate.run<List<User>>(() {
    final List<dynamic> list = jsonDecode(rawJson);
    return list.map((j) => User.fromJson(j)).toList();
  });
}

class HeavyWorker {

What is SSL Pinning, and how does it work? Advanced

How do you implement end-to-end encryption for API payloads? Advanced

+

E2E encryption ensures data is encrypted on the client and decrypted only on the intended server — even intermediary proxies can't read it.

The Process

  1. Key Exchange — Client fetches server's public key (RSA/ECDH)
  2. Generate Session Key — Client generates a random AES-256 key
  3. Encrypt Payload — Encrypt data with AES-256-GCM (symmetric, fast)
  4. Encrypt Session Key — Encrypt the AES key with server's RSA public key
  5. Send Both — Send encrypted payload + encrypted session key
  6. Server Decrypts — Server uses RSA private key → gets AES key → decrypts payload
Dart — E2E Encryption Flow 
import 'package:encrypt/encrypt.dart' as encrypt;
import 'package:pointycastle/export.dart';

class E2EEncryption {
  // Step 1: Generate random AES-256 key
  static encrypt.Key generateSessionKey() {
    return encrypt.Key.fromSecureRandom(32); // 256-bit
  }

  // Step 2: Encrypt payload with AES-256-GCM
  static Map<String, String> encryptPayload(String plainText, encrypt.Key key) {
    final iv = encrypt.IV.fromSecureRandom(12); // 96-bit IV for GCM
    final encrypter = encrypt.Encrypter(encrypt.AES(key, mode: encrypt.AESMode.gcm));
    final encrypted = encrypter.encrypt(plainText, iv: iv);
    
    return {
      'data': encrypted.base64,
      'iv': iv.base64,
    };
  }

  // Step 3: Encrypt AES key with RSA public key
  static String encryptSessionKey(encrypt.Key sessionKey, RSAPublicKey publicKey) {
    final encrypter = encrypt.Encrypter(encrypt.RSA(publicKey: publicKey));
    return encrypter.encrypt(sessionKey.base64).base64;
  }

  // Complete E2E encrypted API call

What is Android Keystore, and how do you use it? Advanced

+

The Android Keystore System provides hardware-backed (TEE/StrongBox) storage for cryptographic keys. Keys stored here:

  • Are protected by biometric authentication if configured
  • Survive app reinstallation if setIsStrongBoxBacked(true)

Kotlin — Android Keystore Usage 
import android.security.keystore.KeyGenParameterSpec
import android.security.keystore.KeyProperties
import java.security.KeyStore
import javax.crypto.Cipher
import javax.crypto.KeyGenerator

class SecureStorage {
    private val keyAlias = "my_secure_key"
    
    // Generate or retrieve AES key from Keystore
    fun getOrCreateKey(): javax.crypto.SecretKey {
        val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
        
        keyStore.getKey(keyAlias, null)?.let { return it as javax.crypto.SecretKey }
        
        // Generate new key in hardware-backed Keystore
        val keyGenerator = KeyGenerator.getInstance(
            KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore"
        )
        keyGenerator.init(
            KeyGenParameterSpec.Builder(keyAlias,
                KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
                .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
                .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
                .setKeySize(256)
                .setUserAuthenticationRequired(true)  // Require biometric
                .setUserAuthenticationValidityDurationSeconds(300) // 5 min
                .build()
        )
        return keyGenerator.generateKey()
    }
    
    fun encrypt(data: ByteArray): Pair<ByteArray, ByteArray> {
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(Cipher.ENCRYPT_MODE, getOrCreateKey())
        return Pair(cipher.doFinal(data), cipher.iv)
    }
}

1. What are Kotlin Coroutines?

Coroutines are lightweight cooperative threads. Thousands of coroutines can run on a handful of OS threads without memory overhead because suspending a function does not block the underlying thread — it simply preserves stack state and yields execution.

  • Dispatchers: Dispatchers.Main (UI updates), Dispatchers.IO (Network/Disk), Dispatchers.Default (Heavy CPU sorting/parsing).
  • Structured Concurrency: Coroutines run inside a CoroutineScope (e.g. viewModelScope). If the parent scope is cancelled, all child coroutines cancel automatically, preventing memory leaks.

An Armstrong number (narcissistic number) is a number where the sum of its digits each raised to the power of the number of digits equals the number itself. Example: 153 = 1³ + 5³ + 3³ = 1 + 125 + 27 = 153

import 'dart:math';

Future<bool> isArmstrong(int number) async {
  // 2-second delay as required
  await Future.delayed(const Duration(seconds: 2));
  
  final digits = number.toString().split('');
  final power = digits.length;
  
  final sum = digits.fold<int>(0, (acc, digit) {
    return acc + pow(int.parse(digit), power).toInt();
  });
  
  return sum == number;
}

Future<List<int>> getArmstrongs(int from, int to) async {
  final List<int> armstrongs = [];
  
  for (int i = from; i <= to; i++) {
    if (await isArmstrong(i)) {
      armstrongs.add(i);
    }
  }
  
  return armstrongs;
}

How do you detect, profile, and fix Memory Leaks in Flutter? Lead Level

+

Memory leaks in Flutter are typically caused by objects being held in memory because of active references long after their corresponding widget has been disposed.

Top 5 Root Causes of Leaks in Flutter

  1. Undisposed Controllers: Failing to call dispose() on AnimationController, TextEditingController, or ScrollController.
  2. Uncancelled Stream Subscriptions: Listening to a continuous Stream or Firebase snapshot without calling subscription.cancel() in dispose().
  3. Retaining BuildContext Across Async Gaps: Closures capturing context that outlive the widget, keeping the entire element subtree retained in memory.
  4. Global Event Listeners: Registering observers with WidgetsBinding.instance.addObserver(this) or event buses without removing them.
  5. Unbounded Image Caching: Loading hundreds of high-res network images without capping PaintingBinding.instance.imageCache.maximumSizeBytes.

How to Profile Using Flutter DevTools

  • Memory Tab & Heap Snapshot: Take Snapshot 1 → navigate into the suspect feature → navigate back → take Snapshot 2 → Diff Snapshots. If state classes or render objects persist after pop, a leak exists.
  • Allocation Tracing: Tracks stack traces of where surviving instances were allocated.
  • Leak Tracking Package: Integrate the official leak_tracker package into widget tests to automatically flag leaks during CI/CD.

How do you design a scalable Offline-First architecture in Flutter? Architecture

+

In enterprise applications, an offline-first architecture treats the local database as the Single Source of Truth (SSOT). The UI never waits for the network to render.

Core Architecture Pillars

  1. Local-First Storage (SSOT): UI observes a reactive local database (Drift/SQLite, Isar, or Hive). Network responses update the local database; the local database emits new states to the UI.
  2. Optimistic UI Updates: User actions (e.g. creating an order) write to the local database immediately with a SyncStatus.pending flag. The UI reflects the change instantly (0ms latency).
  3. Background Sync Queue: A persistent queue stores pending operations. When network connectivity is restored (monitored via connectivity_plus), the queue replays operations in chronological order.
  4. Conflict Resolution Strategies:
    • Last-Write-Wins (LWW): Uses server-assigned timestamps. Simplest, but risk of overwriting concurrent edits.
    • Server-Wins / Client-Wins: Strict deterministic precedence based on business rules.
    • Version Vectors / CRDTs: Conflict-free replicated data types for collaborative documents or notes.
Dart — Offline-First Repository Pattern 
class OrderRepository {
  final LocalDatabase _localDb;
  final ApiClient _apiClient;
  final SyncQueue _syncQueue;

  // 1️⃣ UI reads exclusively from local DB stream (instant 0ms render)
  Stream<List<Order>> watchOrders() => _localDb.watchAllOrders();

  // 2️⃣ Optimistic write
  Future<void> createOrder(Order order) async {
    final pendingOrder = order.copyWith(syncStatus: SyncStatus.pending);
    await _localDb.insertOrder(pendingOrder); // Instant local display
    
    // Add to persistent queue
    await _syncQueue.enqueue(SyncAction(
      endpoint: '/orders',
      method: 'POST',
      payload: order.toJson(),
    ));

    // Trigger sync in background if connected
    _triggerSync();
  }

  // 3️⃣ Background Sync Engine
  Future<void> _triggerSync() async {
    final pendingActions = await _syncQueue.getPending();
    for (final action in pendingActions) {
      try {
        final result = await _apiClient.post(action.endpoint, data: action.payload);
        await _localDb.updateOrder(Order.fromJson(result.data)..syncStatus = SyncStatus.synced);
        await _syncQueue.markCompleted(action.id);
      } catch (e) {
        if (e is SocketException) break; // Still offline, stop draining
        // Handle 409 Conflict using business resolution logic
      }
    }
  }
}

What is SSL Pinning and How Does It Work? Security

+

SSL/TLS Pinning ensures that the client application communicates only with the designated, pre-identified server. It bypasses the operating system's default Certificate Authority (CA) Trust Store, rendering Man-in-the-Middle (MITM) proxy sniffers (Burp Suite, Charles Proxy, Fiddler) completely ineffective.

Handshake Interception & Verification Flow

  1. Client sends ClientHello to the server.
  2. Server returns its X.509 certificate chain (Leaf → Intermediate → Root CA).
  3. Instead of merely trusting the OS Root CA store, the client intercepts the URLAuthenticationChallenge.
  4. The client extracts the public key info (SPKI) or certificate bytes, computes the SHA-256 digest, and checks it against the hardcoded hash.
  5. If the hash matches, the connection proceeds; if mismatched, the challenge is aborted immediately.
Swift — URLSessionDelegate Pinning 
func urlSession(
    _ session: URLSession,
    didReceive challenge: URLAuthenticationChallenge,
    completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void
) {
    guard challenge.protectionSpace.authenticationMethod == NSURLAuthenticationMethodServerTrust,
          let serverTrust = challenge.protectionSpace.serverTrust else {
        completionHandler(.cancelAuthenticationChallenge, nil); return
    }

    // 1. Verify standard anchor integrity
    var secError: CFError?
    guard SecTrustEvaluateWithError(serverTrust, &secError) else {
        completionHandler(.cancelAuthenticationChallenge, nil); return
    }

    // 2. Extract Server Public Key (SPKI)
    guard let cert = SecTrustGetCertificateAtIndex(serverTrust, 0),
          let pubKey = SecCertificateCopyKey(cert),
          let keyData = SecKeyCopyExternalRepresentation(pubKey, nil) as Data? else {
        completionHandler(.cancelAuthenticationChallenge, nil); return
    }

    // 3. Compare SHA-256 hash against pinned hash
    let hash = SHA256.hash(data: keyData)
    let hashBase64 = Data(hash).base64EncodedString()

    if hashBase64 == "WoiWRyIOVNa9ihaBciRSC7XHjliYS9VwUGOIud4PB18=" {
        completionHandler(.useCredential, URLCredential(trust: serverTrust))
    } else {
        completionHandler(.cancelAuthenticationChallenge, nil) // Reject MITM!
    }
}

SSL Pinning: Handling Expiring Certificates & Zero-Downtime Backup Process Production

+

The Nightmare Scenario: If you pin a single leaf certificate and it expires, any user who hasn't downloaded the latest app update will be permanently locked out of all backend services.

Zero-Downtime Enterprise Rotation Strategy

  • 1. Pin the SPKI Public Key (Subject Public Key Info), NOT the Leaf Certificate: When renewing the TLS certificate, reuse the existing Certificate Signing Request (CSR) and private key. The certificate changes, but the public key hash remains identical — zero app update needed!
  • 2. Multi-Key Pinning (Dual-Pinning / N+1 Backup Keys): Always embed at least two pins:
    • Primary Pin: Active production public key.
    • Backup Pin: Cold standby key generated in an offline secure HSM.
    • Intermediate CA Pin: Trusted CA authority public key as an emergency failsafe.
  • 3. Dynamic Remote Pinning with Cryptographic Verification: Maintain an encrypted, digitally signed pin configuration hosted on a CDN or cloud worker. If pinning fails, fetch the signed configuration, verify its RSA/ECDSA signature against an embedded master key, update Keychain, and reconnect.
⚠️
Interviewer Trap Question

"Why not pin the Root CA certificate?"
Answer: Pinning the Root CA weakens security because any fraudulent certificate issued by that same CA (or rogue intermediate authority under that CA) would pass validation, leaving you vulnerable to nation-state or enterprise proxy MITM.

How RSA Encryption Works Deep Dive Cryptography

+

RSA is founded on the prime factorization hardness problem — multiplying two large primes is trivial, but factoring their composite product back into primes is mathematically infeasible for classical computers.

Key Generation Algorithm

  1. Choose two very large prime numbers: p and q.
  2. Compute modulus: n = p × q.
  3. Compute Euler's totient: φ(n) = (p - 1)(q - 1).
  4. Select public exponent e such that 1 < e < φ(n) and gcd(e, φ(n)) = 1 (typically 65537).
  5. Compute private exponent d such that: d × e ≡ 1 (mod φ(n)).
  6. Public Key: (e, n) • Private Key: (d, n).

Encryption & Decryption Mathematics

  • Encrypt: Ciphertext = (Message)^e mod n
  • Decrypt: Message = (Ciphertext)^d mod n

Payload Size Limit & OAEP Padding

For a 2048-bit RSA key (256 bytes), using OAEP padding with SHA-256:

Max Payload = 256 bytes - (2 × 32) - 2 = 190 bytes.

Because you cannot encrypt more than 190 bytes with RSA-2048, you never encrypt large API payloads with RSA directly. Instead, you encrypt a random 32-byte AES key using RSA, and encrypt the large payload using that AES key (Hybrid Scheme).

ARC (Automatic Reference Counting) & Memory Management iOS

+

Swift manages heap memory using ARC, tracking the number of active strong references to each class instance. When retain count drops to 0, memory is instantly reclaimed.

Retain Cycles & Capture Lists

When two objects strongly reference each other, their retain count never reaches 0. Break cycles using [weak self] in escaping closures:

  • weak: Zeroing weak reference; automatically becomes nil if deallocated (must be optional).
  • unowned: Non-zeroing reference; assumes target is alive. Crashes with EXC_BAD_ACCESS if accessed after deallocation.
  • autoreleasepool: Drains temporary autoreleased Objective-C objects immediately in tight loops rather than waiting for RunLoop idle.

Scenario: App Crashes in Production but Never in Development Troubleshooting

+

This is a classic senior interview scenario. Here is how to systematically troubleshoot and resolve it:

1. Root Cause Analysis (Why Prod Behaves Differently)

  • Compiler Optimization Level: Dev builds run with -Onone; Release builds run with -O (Fast) or -Osize. Optimizations reorder instructions, inline methods, and expose dormant multithreaded data races.
  • Minification & Code Stripping: ProGuard / R8 (Android) or aggressive dead-code stripping may have obfuscated or stripped reflection-based JSON model fields.
  • Environment Discrepancies: Release builds enforce strict SSL Pinning and production endpoints; dev builds bypass cert verification or use local proxies.
  • Missing Release Entitlements: Push notification entitlements or Keychain Access Groups misconfigured in Release provisioning profiles.

2. Systematic Resolution Strategy

  1. Fetch raw crash reports and symbolicate using the exact matching **dSYM / mapping.txt** via Firebase Crashlytics or Xcode Organizer.
  2. Run a local Release build connected to LLDB: flutter run --release or Xcode Run Scheme configured with Build Configuration = Release.
  3. Inspect Xcode Thread Sanitizer (TSan) for data races.

Scenario: Displaying >200MB Massive Dataset with Minimum Waiting Performance

+

The Challenge: Parsing a 200MB JSON payload on the main thread will lock the UI event loop for seconds, triggering iOS watchdog kill (0x8badf00d) or Android ANR.

Architectural Solution

  • 1. Offload to Background Isolate / Task: In Flutter, run JSON parsing in a separate memory space using Isolate.run(); in Swift, use background cooperative tasks with URLSession.bytes.

  • 3. Viewport Virtualization: Use ListView.builder (Flutter) or UICollectionViewDiffableDataSource (iOS) to instantiate only the 10-15 rows visible in the viewport.

Scenario: Platform Channel Implemented but No Data Received in Flutter Debugging

+

Checklist for Silent Platform Channel Failures

  1. Registration Timing: If Flutter calls the platform channel during startup before setMethodCallHandler is registered in native AppDelegate / MainActivity, the call is dropped silently.
  2. Main Thread Dispatch: Native responses must be dispatched back to Flutter on the Platform Main UI Thread. Calling result(data) from a background GCD queue fails:
    DispatchQueue.main.async { result(data) }.
  3. Typo in Channel or Method Name: Method names are string-matched; ensure exact casing across Dart and Swift.
  4. Uncaught Native Exception: If native code throws an unhandled exception before reaching result(...), Flutter hangs indefinitely. Always wrap in do-catch and call result(FlutterError(...)).

Beyond MethodChannels: Dart FFI & Type-Safe Pigeon Interop

+

Standard MethodChannel serializes and copies every payload byte across the platform boundary on the main thread, introducing overhead for video frames, cryptography, or heavy BLE streams.

Modern High-Performance Alternatives

  • Pigeon (Type-Safe Code Generation): Compiles a shared interface schema into strongly typed Swift, Kotlin, and Dart classes. Eliminates string method matching and runtime type casting.
  • Dart FFI (dart:ffi - Foreign Function Interface): Directly calls native C/C++/Rust dynamic libraries (.dylib / .so) with zero serialization overhead, sharing memory pointers directly. Ideal for high-speed cryptographic hashing and image manipulation.
